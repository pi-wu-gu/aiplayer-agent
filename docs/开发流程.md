# AI Agent 系统 · 开发流程

> 项目位置：`PCL2/agent/`（与 `PCL2/AI/` 同级）
> 目标：为 MC AI 玩家（`PCL2/AI/` 桥接系统）提供决策层 agent，同时是一套通用的多 agent 框架。
> 配套文档：《参数清单.md》《可行性分析与查漏补缺.md》《../AI/docs/操作注意事项.md》（MC 桥接协议）

> **📌 进度快照（2026-10-18）**：阶段 0-3 已完成并实跑；阶段 4（自研工具）在 agent 侧未做，
> 但模组侧用**声明式宏**（`tool_run`，受 `[permissions].selfToolEnabled` 门控）实现了等价能力；
> 阶段 5 在持续运行中积累了实战数据。**本文第三节保留原始设计意图与验收标准**（勿当现状读），
> 实际能力清单见 `../README.md`「工具面」与「当前状态」。

## 一、总体架构（自下而上四层）

```
┌─────────────────────────────────────────────────┐
│ L5 决策层（最终形态）：MC 生存决策 agent 挂桥接     │
├─────────────────────────────────────────────────┤
│ L4 协同层：orchestrator 主 agent                  │
│    ├─ spawn_subagent(role, model, task)          │
│    └─ 结果回收 / 深度与并发限制 / token 预算        │
├─────────────────────────────────────────────────┤
│ L3 能力层：tool_registry（内置工具 + 自研工具热载） │
│    └─ tool_maker：LLM 写代码 → 校验 → 沙箱 → 注册  │
├─────────────────────────────────────────────────┤
│ L2 模型层：llm_client（OpenAI 兼容多 provider）     │
│    └─ keys.yaml 手动添加 / balance 余量查询        │
├─────────────────────────────────────────────────┤
│ L1 配置层：config.yaml（全局）+ keys.yaml（密钥）   │
└─────────────────────────────────────────────────┘
```

设计原则：
1. **配置驱动**——所有 provider/key/模型/角色都是数据文件，加能力=改文件不改代码。
2. **工具即接口**——LLM 只通过工具与环境交互（含创建次级 agent、开发新工具本身也是工具）。
3. **沙箱边界**——自研工具必须过校验+沙箱才能注册；次级 agent 权限默认不大于创建者。

## 二、目录规划

```
agent/
├── run.py                  # 入口：python run.py [--role primary] [--task "..."]
├── config/
│   ├── config.yaml         # 全局：默认provider/模型、agent限制、沙箱规则、日志
│   └── keys.yaml           # 密钥（手动添加，永不进日志/git）
├── core/
│   ├── config_loader.py    # 两级配置加载+校验
│   ├── llm_client.py       # 统一 chat/completions（含工具调用）、重试退避、用量记账
│   ├── balance.py          # 余量查询 adapter（按 provider 分发）
│   ├── agent.py            # Agent 基类：系统提示+工具循环+记忆
│   ├── orchestrator.py     # 主 agent、spawn/join、并发池
│   ├── tool_registry.py    # 工具注册表（json-schema 校验参数）
│   ├── tool_maker.py       # 自研工具流水线（生成→校验→沙箱→注册→落盘）
│   └── memory.py           # 会话历史 + JSONL 落盘
├── tools/
│   ├── builtin/            # 内置工具（每个文件一个工具，manifest+实现）
│   │   ├── mc_bridge.py    # MC 桥接：读 /state、发 /command、等动作结果
│   │   ├── file_io.py      # 受限文件读写（限定 agent/ 目录）
│   │   ├── balance_query.py# 查 key 余量
│   │   └── spawn_subagent.py
│   └── custom/             # agent 自研工具落盘处（自动加载）
├── agents/                 # 角色定义（yaml）：prompt、可用工具白名单、允许的模型档位、可创建的次级角色
├── docs/                   # 本文档与可行性分析
├── tests/                  # 离线测试（mock LLM）
└── logs/                   # 运行日志 + 用量账本（jsonl）
```

## 三、开发阶段（每阶段有明确验收标准）

### 阶段 0：配置系统（0.5 天）
- `config.yaml` + `keys.yaml.example` 模板；`config_loader` 加载/校验/合并。
- key 字段：`name / base_url / api_key / protocol(openai-compat) / balance_api(auto|none|one-api) / notes`。
- **验收**：填入真实 DeepSeek key 后 `python run.py --check` 打印 provider 状态表。

### 阶段 1：模型层（1 天）
- `llm_client`：纯 `requests` 实现 OpenAI 兼容 `/chat/completions`（stream 可后置）、工具调用消息格式、429/超时指数退避重试。
- 用量记账：每次调用记录 tokens/耗时/provider/model → `logs/usage_YYYYMMDD.jsonl`。
- `balance` adapter 首批：DeepSeek（`/user/balance`）、one-api 类中转（`/v1/dashboard/billing/subscription+usage`）；其余标"不支持自动查询"。
- `get_available_models`：各 provider `/v1/models`。
- **验收**：`run.py --check` 输出每个 key 的连通性+余量+模型列表。

### 阶段 2：Agent 核心 + 工具注册（1-2 天）
- `Agent` 基类：系统提示、工具循环（function call → registry 执行 → 结果回填）、最大轮数/超时。
- `tool_registry`：工具=（manifest: name/description/params json-schema + 实现）；参数 schema 校验。
- 内置工具首批：`mc_state`（读 /state）、`mc_act`（发动作并轮询 last_action 结果）、`file_read/file_write`（限定 agent 目录）、`balance_query`。
- **验收**：单 agent + MC 工具完成"读状态→发现夜晚→sleep"闭环（离线 mock + 在线各一次）。

### 阶段 3：多 agent 协同（1-2 天）
- `spawn_subagent(role, model, task, timeout)` 工具；角色定义 yaml（prompt/工具白名单/可创建次级/允许模型档位）。
- 限制（防失控）：最大嵌套深度 2（主→次→不可再建）、并发次级 ≤4、单次级 token 预算、总预算熔断。
- 结果回收：次级返回结构化 `report{status, summary, data}`。
- **验收**：主 agent 同时派 2 个次级（一个查余量、一个读 MC 状态）并汇总。

### 阶段 4：自研工具（2 天）
- `develop_tool(requirement)` 工具：LLM 生成代码 → AST 静态检查（禁止 os.system/subprocess/eval/网络白名单外访问/越界路径）→ 隔离 subprocess 试运行（超时杀死）→ 生成 manifest → 注册+落盘 `tools/custom/`。
- 自研工具默认仅本 agent 会话可用；跨会话生效需用户确认（防恶意/低质代码沉淀）。
- **验收**：让 agent 自研一个"把 state 快照写成 markdown 报告"的工具并成功使用。

### 阶段 5：MC 决策层实战（持续）
- 角色 `mc_survival_primary`：每 N 秒读 state → 决策（睡觉/进食由护符自理，专注避险/任务执行）→ 派次级做专项（侦察/建造/搬运）。
- 长期记忆：重要结论写 `memory/` 供后续会话注入。
- **验收**：连续 1 小时无人值守挂机存活率 100%。

## 四、风险与对策（开发期守则）

| 风险 | 对策 |
|---|---|
| key 泄漏 | keys.yaml 单独存放、日志脱敏、git 忽略 |
| LLM 成本失控 | usage 账本 + 每 agent 会话预算 + 总熔断余额阈值（配合余量查询自动停机） |
| 自研工具恶意/劣质代码 | AST 白名单 + 沙箱试运行 + 跨会话人工确认 |
| 递归创建 agent | 深度/并发硬限制写在 orchestrator，工具层不可绕过 |
| MC 桥接断连 | mc_bridge 工具带健康检查；断连只报告不重试风暴 |

## 五、与既有 MC 系统的对接约定

- 控制面：aiplayer 模组 `http://127.0.0.1:8780`（旧 JsMacros 桥 8765 已废弃；协议兼容：`GET /state` + `POST /command {"commands":[...]}`，动作结果在 **/state 的 last_action** 可见）。
- MC 侧协议细节全部以《AI/docs/操作注意事项.md》为准（槽位映射/失步/红线），agent 层**不直连游戏**，一切经由桥接。
