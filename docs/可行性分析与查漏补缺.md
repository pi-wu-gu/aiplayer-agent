# 可行性分析与查漏补缺

> 对应需求：①手动添加 key 和 API ②查询余量 ③多 agent 协同 ④初级创建次级并选模型 ⑤自行开发工具
> 结论先行：**五项需求全部可行，无根本性障碍**；主要工作量在"余量查询的多平台适配"与"自研工具的安全沙箱"。

## 需求逐项分析

### ① 手动添加 key 和 API —— 可行性：高
- 国内主流（DeepSeek / Moonshot Kimi / 硅基流动 / 火山方舟 / 各类 one-api 中转站）几乎全部兼容 **OpenAI `/v1/chat/completions` 协议**，只需 `base_url + api_key` 两个参数即可统一接入。
- 设计：`keys.yaml` 手动编辑，一条记录一个 provider；`config_loader` 启动校验（连通性 ping）。
- **查漏**：
  - ✅ 已列入：key 永不进日志、模板文件 `keys.yaml.example` 供复制。
  - ⚠️ 补缺 1：`api_key` 应支持环境变量引用（`$DEEPSEEK_KEY`），避免明文。
  - ⚠️ 补缺 2：同一 provider 多 key 轮换（一个 key 限流时自动切下一个）——列入阶段 1 可选。

### ② 查询余量 —— 可行性：中高（分平台）
| 平台 | 余额端点 | 难度 |
|---|---|---|
| DeepSeek | `GET /user/balance` → `balance_infos[].total_balance` | 简单（首选实现） |
| one-api / new-api 中转 | `GET /v1/dashboard/billing/subscription` + `/usage`（OpenAI 旧版计费格式） | 简单（覆盖大量中转站） |
| Moonshot | `GET /v1/users/me/balance` | 简单 |
| 硅基流动 | `GET /v1/user/info` → `data.balance` | 简单 |
| 智谱 / 百炼 | 无公开余额 API | 标"网页自查" |
| OpenAI 官方 | 需 admin key 的 billing API | 后置 |
- 设计：`balance_api: auto|none|one-api` 字段，`auto` 按 base_url 域名特征猜协议，猜不到则探测一次。
- **查漏**：
  - ⚠️ 补缺 3：余额查询结果要同时进**成本熔断**——总余额低于阈值（config 可设）时 agent 自动只读不写/停机，防止打光最后一分钱。
  - ⚠️ 补缺 4：余额≠可用额度（有的平台送券与充值分开），adapter 需保留原始字段不硬解析。

### ③ 多 agent 协同 —— 可行性：高
- 单机单进程即可满足（当前场景无跨机需求），orchestrator 进程内持有次级 agent 对象，无需消息队列/中间件。
- 协同模式 MVP：**主从任务制**——主 agent 用 `spawn_subagent` 派活（同步等待或批量并发），次级返回结构化报告。后续可加"次级间互发消息"，非必需。
- **查漏**：
  - ⚠️ 补缺 5：上下文隔离——次级只拿 task 描述 + 自己的工具结果，**不继承主 agent 的完整对话**（否则 token 爆炸）。需要"传什么给次级"由主 agent 显式决定的约定。
  - ⚠️ 补缺 6：并发写冲突——两个次级同时 `file_write` 同一文件。对策：内置文件工具加进程内锁；MC 动作命令本身有队列，天然串行。
  - ⚠️ 补缺 7：死循环/卡死次级——spawn 带 timeout，超时杀线程并返回超时报告。

### ④ 初级创建次级并选择模型 —— 可行性：高
- `spawn_subagent(role_id, model, task)`：`model` 从"已注册 provider 的模型列表"选（阶段 1 的 `/v1/models` 结果缓存）；角色 `agents/*.yaml` 定义 prompt 与工具白名单。
- **查漏**：
  - ⚠️ 补缺 8：**模型可用性校验**——主 agent 选的模型必须在该 role 的允许档位内（角色 yaml 的 `allowed_models`，如 `any | cheap | tier1`），且该 provider 真实提供；否则 spawn 拒绝并回显可用列表。
  - ⚠️ 补缺 9：成本提示——贵模型（config 标价表）创建时给主 agent 一条确认性提示，但不阻塞。
  - ⚠️ 补缺 10：次级的次级——默认禁止（深度 2 封顶），角色 yaml 可显式放开（`can_spawn: true`）。

### ⑤ 自行开发工具 —— 可行性：中高（安全设计是关键）
- 流水线：`develop_tool(requirement)` → LLM 生成 `manifest(params json-schema) + 代码` →
  **AST 静态检查**（黑名单：`os.system / subprocess / eval / exec / __import__ / open 越出 agent 目录 / 非白名单网络地址`）→
  **沙箱试运行**（独立 subprocess，空参数/样例参数，超时 10s 杀）→ 注册（仅当前会话）+ 落盘 `tools/custom/`。
- **查漏**：
  - ⚠️ 补缺 11：AST 白名单挡不住所有恶意模式（动态字符串拼接 import 等）——因此双保险：落盘后**跨会话生效需用户确认**；沙箱 subprocess 用受限环境变量 + 禁网（MVP 阶段自研工具默认禁网络访问，白名单显式放开）。
  - ⚠️ 补缺 12：工具版本管理——同名覆盖前保留 `.bak`；`tools/custom/` 加载失败的工具记日志并跳过，不阻断启动。
  - ⚠️ 补缺 13：manifest 与代码不匹配（声明参数与实际不符）——沙箱阶段用 schema 随机样例强制对齐测试。

### ⑥（隐含）与 MC 桥接整合 —— 可行性：高
- 桥接协议已完全文档化且稳定运行（今日全链路验证），`mc_state`/`mc_act` 两个工具即可覆盖全部游戏操作。
- **查漏**：
  - ⚠️ 补缺 14：动作结果异步——发命令后结果在下一次 /state 的 `last_action`，`mc_act` 必须内置轮询等待（含超时），否则 agent 拿不到执行结果。
  - ⚠️ 补缺 15：MC 侧安全红线（不攻击玩家/不失步操作/100 字聊天限制）必须写进 MC 角色 system prompt——技术层挡不住 LLM 乱决策，红线靠提示词+桥接侧动作白名单双层约束。

## 依赖与运行环境

- Python 3.13（已有 managed 版）；依赖仅 `requests` + `pyyaml`（装入隔离 venv，不污染全局）。
- 无需数据库：记忆/账本用 JSONL；无 GPU；纯 API 调用。

## 结论

1. **立即可开工**：阶段 0/1 只需一个有效 DeepSeek key（用户已有）。
2. 最大不确定性仅一个：**智谱/百炼类无余额 API 的平台**——不影响主流程，标记"网页自查"即可。
3. 自研工具的安全边界是唯一需要"设计先行"的点，已在阶段 4 给出双保险方案。
